# AWANA database ("Gonkulator")

The roster, attendance, games, awards, progress and print reports for the club, as one browser app plus one data file. The app runs in the browser tab with no server of its own; the data file goes only where you save it: this computer, or your own Google Drive when saving there is turned on. What changed in each version is in `CHANGELOG.md`.

## Folder layout

- `dev/` is the working directory: the app (`dev/app/`), the tools (`dev/tools/`), the tests (`dev/app/test/`), the current data file and the current Planning Center export. This is where we edit and test.
- **Statistics** tab (`stats.js`, `app-stats.js`): three buttons show one group at a time (`aria-pressed`, local to `app-stats.js`; the choice survives a redraw and keeps keyboard focus; one row on a phone). **Attendance**: the whole club, attendance by class, most nights present (children and adults), Participation and Extra by class. **Progress, awards and pace**: *Section pace by class*, *Sparks pace* (awards earned per night attended), then most awards and points leaders; pace, awards and progress are one group on purpose, because finished sections lead to awards and both are counted per night attended. **Color teams**: team points. Adults are marked on the Attendance tab under *Volunteers*. **Dark mode** follows the device setting (CSS variables in `style.css`; reports stay on white paper and printing is always light) and the layout has a phone breakpoint at 760px, where the tab strip becomes a menu button (the current tab and the To do count) and the To do cards wrap instead of scrolling sideways.
- **Pace** (`pace.js`, pure; drawn by the Progress sheet, the *Pace watch list* report and Statistics; nothing is stored): how fast each Sparks and T&T child signs off sections, per night **attended** (never per calendar week). *Core* sections are the dated items that earn a book or emblem (Sparks: Flight 3:16, Rank, jewel sections 1-4; T&T: Start Zones and the emblem sections); Sparks reviews and T&T Silver/Gold are counted separately and never move pace. A section lands on the first night the child was present on or after its sign-off date, so a month signed off in one visit by a child who comes every other week is one big night. The numbers (`Pace.CFG`: `GOAL` 1, `SLOW` 0.5, `WATCH` 0.75, `WINDOW` 4 nights, `MIN_NIGHTS` 3, `QUIET` 3, `DROP` 0.6, `RISE` 1.4, `FIRST_NIGHT` 3) are first guesses to tune on real sign-off dates. A child is in at most one list: *capable, slowed*, *steadily slow*, or *needs encouragement*; a class with no sign-offs entered shows "not entered". The pace strip on the Progress sheet links to the watch list for the child's class. No pass type, score, attempts or signer is recorded (several attempts a day are the room leader's call), so room-against-room pace is a reason to go and watch, never proof of a different standard. Tested by `test/pace.test.js`.
- **Phones, tablets and keyboards.** On a phone (under 760px) only the tab menu button sticks, *Recent places* scrolls away, **Download data file** is the first button in the top bar, the Progress sheet repeats *Previous child / Next child* at its foot, and Attendance repeats the "N of M present" count under the table. Touch targets are 44px under 760px and, on a touch tablet, under `(pointer: coarse) and (min-width: 761px)` (Attendance checkboxes, the Progress dates, Today buttons and pickers). On a desktop the title bar and tab strip stay on top while the page scrolls (`#stickyTop`; `app.js` keeps `--stickyh` up to date for the table headings and the Apply bar). Keyboard: every control has a visible focus ring and a name; Tab wraps inside an open dialog and Esc cancels it; the tab strip moves with the arrow keys, Home and End; `/` focuses the manual's search; `P` on an Attendance checkbox opens the child; Ctrl+Z / Ctrl+Y undo and redo outside text boxes. Screen readers: bare inputs inside table cells get a name from their column heading and row (`nameCells` in `app.js`), one-row layout tables are marked presentational, and each tab's page is a labeled region. Tested by `test/a11y-browser.test.js`, `test/no-nested-scroll-browser.test.js` and `test/mobile-audit.js`; what was checked and what was not (no real screen reader, 200% zoom, Windows high contrast, Firefox, Safari) is in `UX-REVIEW-2026-11-03.md`.
- **One bar for "changes".** The bar under the tabs (`drawDraftBar` in `app-season.js`) holds held changes (Apply / Discard) on tabs that hold them, and the count of changes Planning Center still needs (edits made here to a Planning Center field, `ov:` values; a link opens the *Changes needed in Planning Center* report): under the Apply line on those tabs, alone on any other tab. The top line shows that count only while no season is open, and "unsaved" is said once, on the Data file line. Tested by `test/pcneed-bar-browser.test.js`.
- **Options** tab (`app-options.js`): the book list, the club settings, and the settings kept in the data file (`season.config`): `teamOrder` (the order the four colors are listed in on every screen; `Season.teamOrder(season)` reads it and falls back to red, yellow, green, blue), `yearBook` (this year's book per group, `{ Cubbies, Sparks, 'T&T' }`: offered in the Handbook box of a child with no handbook and opened first on Progress for Sparks; `Season.yearBook(s, group)` checks it; `newSeason` clears it), `sparksBooks` (`'sequence'`, Awana's standard, or `'together'`, the All Together method, which is what gives Sparks a year book; carries into a new season), `placePoints`, `blueJewelWeeks`, plus the store settings and the Drive folders, which are the same settings as on the Awana store points tab and the Google Drive dialog (one change handler, `App.storeSettings`). Tested by `test/options.test.js` and `test/options-browser.test.js`.
- **Color teams** (`teams.js` the solver, `teamplan.js` the year plan, `app-teamgrid.js` the grid, `app-options.js` the balancing goals; reference: `docs/reference/COLOR-TEAMS.md`): the Color team games tab's Color teams view is a year grid (Q1 to Q4 for every child, by class, group or whole club) in which each quarter is locked, ready to lock or projected. `teamplan.js` is pure logic (quarter states, locks, pins, attendance turnout, projection, minimum-change recalculation, balance notes, priorities); `app-teamgrid.js` only draws it and wires its buttons. Colors stay in `team:Q1..Q4` on each person; the plan adds only `config.teamPlan` (below). Tested by `test/teamplan.test.js` and `test/teamgrid-browser.test.js`.
- **Recent places** (`app-trail.js`): the strip under the tabs (a menu on a phone) with the last 10 places visited. A place is a tab plus its context; each tab registers `App.places[view] = { get(), set(state) }` (Attendance, Games, Awards, Progress, Person; other tabs are places by themselves). Kept in memory only (it holds children's names) and dropped when another file is opened. Tested by `test/trail-browser.test.js`.
- **(i) notes** (`info.js`, `app-info.js`): a small (i) next to a setting shows a one-line tip on hover and, clicked, the full note as a popup over the page (it never moves the page's content; one at a time; closed by a second click, the x, Esc, a click elsewhere, or a change of tab) on which option to use under what conditions. Desktop only (hidden on a phone by `style.css`). The text lives in one list, `info.js` (`NOTES`); a page puts one on with `<i class="info" data-info="area.name"></i>` (static HTML, or `Info.html('area.name')` in a string a tab builds), and `app-info.js` turns it into a button. The same list is the manual's section 5, *Which option when*, written into `index.html` between `<!-- guide:start -->` and `<!-- guide:end -->` by `node dev/tools/sync-guide.js` (`test/info.test.js` fails when the two differ, when a note is never shown, or when an (i) names a note that does not exist).
- **How it works** (the manual in `index.html`): contents with every section, every tab (in the tab-menu order: Tonight, People, Season, Admin) and every group of notes; a search box (`app-help.js`) that finds a word anywhere in the manual, notes included, lists matches under their section, and scrolls to and marks the words (the `/` key focuses it). The search index is built from the page on first use, so it cannot go stale.
- **Google Drive saving** (`drive.js`, `app-drive.js`): one club files folder for opening and saving, slide images optionally elsewhere; save style in the data file (`config.saveStyleDrive`): *one file updated in place* (default) or *dated files*, with a merge when someone else saved (`Season.merge3`: a three-way merge of what this copy changed since it opened onto the file as it is now; what is already saved is never overwritten, clashes are listed), a check of the revision list after each write for a save in the gap, and a version pinned every `config.drivePinDays` days (default 30). `lineage()` decides whether the open season may update a Drive file at all. The settings are a card on the Options tab (no pop-up: folders, saving on/off, save style, sign-out); the Save and Import buttons are each a split button with a menu and share one default (Drive while saving to Drive is on). Slides, ZIPs and CSV exports go to the second folder. See `GOOGLE-DRIVE.md`.
- **Updates and auto-save** (`app-update.js`; both settings are in the data file, `config.autoUpdate` and `config.autoSave`; nothing is kept in the browser except the open file carried across an Update now reload, below): every `minutes` (10) the page fetches its own `index.html` with a cache-busting query and compares `app-version`/`app-build`; a newer one shows the bar (Update now / Later) and the Options card. *Update now* settles drafts, **saves first** if unsaved (`App.saveNow()`, the Save button's path; resolves when a Drive save finished), puts the session in `sessionStorage` (`awana-handoff`: season JSON, tab, test files, Drive lineage via `App.driveHandoff`), and `location.replace`s to `?updated=<version>`; on load it restores, removes the key at once, and if restoring fails downloads the carried copy as `awana-session-recovered-*.json`. `make-deploy.sh` stamps the published `index.html` with `?v=<version>` on every script and style so the reload fetches new code. Auto-save (`App.autosave`) calls `App.saveNow({ auto: true })` on a timer, only when dirty, never prompting. Tests: `test/update-autosave-browser.test.js`, `test/deploy-stamp.test.js`.
- **Awana store points** tab (`store.js`, `app-store.js`): year-end store points per child from weighted earnings (attendance, handbook, participation, extra, game place and spirit points, awards, sections), kept between a minimum and maximum (default 15 and 200) by one of three methods, shown so far and projected to the end of the year, with each earning's share and the spread by program. Settings are saved in the data file (`config.store`).
- **Google Drive** is optional and off until `dev/app/drive-config.js` is filled in; see `docs/reference/GOOGLE-DRIVE.md`. **Try it out** on the opening screen loads the invented club from `app/try/` (its data file says `"fake": true`, and `Season.freshenFake` moves every date forward by whole weeks so its newest club night is the latest one on or before today: the demo never goes stale; nothing else opens a file that way) (copied from `dev/test-data/` by `make-deploy.sh`, TEST files only); *Try an import* in the red banner then imports the 15 invented registrations.
- `dev/test-data/` holds the **anonymized test set**: a copy of the real data file and export with every name, phone number, email, address, registration ID and birthdate replaced and the medical text made generic (`awana-2026-27-TEST-….json` and `20261028 -- demo-club-2026-27 TEST.csv`), and `20261103 -- demo-club-2026-27 TEST.csv`, the anonymized export plus 15 invented registrations covering the corner cases of an import. `ANONYMIZATION.md` says what was replaced, how birthdates (moved two to eight weeks, same age) and medical notes (generic invented ones) were handled, and what was not changed (grades, classes); `TEST-CASES.md` says what each of the 15 rows tests and what the To do page and file check must show. The demo data file also carries a small color team plan (projected Q3 and Q4, a few hand-set Q3 colors), added by `dev/tools/demo-plan.js` (`node dev/tools/demo-plan.js <demo data file>`; it refuses a file that is not flagged fake, and `make-test-data.js` runs it). Rebuild with `node dev/tools/make-test-data.js <data.json> <export.csv> dev/test-data`, then `node dev/tools/make-test-export.js "<anonymized export>" dev/test-data`; the output is identical each time. The TEST in the names puts the app in test mode (see *Test files* below). Nothing in this folder is real, and `test/anonymized-data.test.js` and `test/import-test-file.test.js` pin that.
- `deploy/` is the only folder deployed from. Pushing `deploy/` to `main` publishes it through GitHub Pages (`.github/workflows/pages.yml`), at https://burnclouds.github.io/awana-directors-tool/. Nothing is copied to Nextcloud; the old `static.burnclouds.net` pages only redirect there. Code only (`.js`, `.html`, `.css`), no data, no tests. Never edit it by hand: run `sh make-deploy.sh`, which refreshes it from `dev/` and stops (before touching `deploy/`) if any other kind of file turns up, if a sample-club file is not marked TEST and `"fake": true`, if a changed script's version was not bumped, or if anything shipped changed while `app-version` and `app-build` did not (phones cache per release, so they would keep the old files).
- The old migration inputs (the CSVs and season JSON the data file was built from, plus the Oct 14 export) and the old Google Sheets exports and PDFs are no longer in this repository: they hold real children's data and were moved out with it, into a private folder outside the repo. Nothing here is read by the app. Never create a folder named `archive/` (`.gitignore` ignores every folder with that name).
- `docs/README.md` is the map of everything else: references, design specs, reviews, research, and the retired notes. `docs/retired/old-google-sheets/SUMMARY.md` says what replaced each tab of the old Google Sheets.
- `CHANGELOG.md` is what changed in each app version. `docs/retired/UX-REVIEW-2026-11-03.md` records the phone, tablet, keyboard and screen-reader review (what was checked, what was changed and why, what was never verified). `docs/retired/` also holds the older code review, the 11-05 mobile feedback and the full backlog as it stood on 2026-11-14. `docs/superpowers/specs/` and `docs/superpowers/plans/` hold design documents and build plans (the Color teams rework is designed there).
- **Git.** `database/` is a git repository. Its public remote is `origin` = `github.com/burnclouds/awana-directors-tool`; only the `public` branch (a single snapshot, pushed as `main`) goes there. The private history is on the local branch `private` (it was `main`) and is never pushed; neither is `public-old-do-not-push`, the old history that once exposed real names. `git push` of any branch other than `public` to `origin main` is a mistake: see "Changing and deploying". `.gitignore` keeps every kind of data file out (`*.csv`, `*.json`, `*.txt`, `*.xlsx`, `*.pdf`, images, `archive/`, `drive-download-*/`, `dev/*.csv|json|txt`), except `package.json` and `package-lock.json`; `node_modules/` and `.superpowers/` (brainstorming mock-ups) are ignored too. Exceptions (narrow, in `.gitignore`, pinned by `test/gitignore.test.js`): the app manifest and icons, and invented files with TEST in the name in `dev/test-data/` and `deploy/app/try/`, so a fresh clone can build and test. `deploy/` (the built app, code only) **is** tracked, so a deploy is committed with the code. Real children's data must never be committed or pushed; a fresh checkout has no data, so the tests that take real-file arguments (see Tests) need your local files.

## The data file

One JSON file named `awana-<year>-<yyyymmdd-hhmmss>.json`. The tag is the time it was downloaded, so **every save is a new file** and the older ones are automatic backups. Always open the newest. It holds children's names and medical details: keep it private.

| Section | What it holds |
|---|---|
| `roster` | Per person (by `x_ClubberID`, `RegID_First_Last`): `pc` = the full Planning Center record as of the last import; `v` = what we own: `x_Active`, `x_InactiveBy` (`import` when an import made the person inactive; anyone else who is inactive was marked by hand and stays inactive when Planning Center still lists them), `x_NoPhotos`, `x_Notes`, `team:Q1`..`team:Q4`, `x_Uni_*` uniform tracking, `ov:<column>` pending Planning Center changes. `pcAsOf`/`pcSource` say which export it came from. |
| `roster.pcExport` | The kept Planning Center export (version 6): when it was imported, a hash (so the same file twice does nothing), its header and the stored column names, row and blank-row counts, which people its rows belong to (`ids`), and the rows that belong to nobody (`loose`). Everything the export said is in the file, used or not; `Model.exportBack` rebuilds it. See `docs/DATA-FORMAT.md` 5.2. |
| `calendar`, `rotation` | The club calendar and the nightly rotation grid. |
| `attendance` | `[date][id] = { a, h, p, x }` present / handbook / participation / extra (1 = yes). Optional `t` = a one-night team (a visitor or fill-in; needs `a`); optional `g` = the group (Puggles, Cubbies, Sparks, T&T) the child was in when Present was ticked, so game points stay with the group of that night after a move (older nights have none and use the group today). A night counts only if it is a club night on the calendar with at least one `a` (`Season.heldNights`); an empty night is removed when its last mark is cleared. |
| `games` | `[date][group][team] = { place 1-4, spirit 0-3 }`. Per team, not per child. |
| `awards` | `[date][id] = [award, ...]` for Puggles, Cubbies, Sparks and T&T: the night each award was **announced** (told to the group). Set by *Mark all announced* on the Awards tab (held awards are skipped) or by the Announced date on the Progress record; clear that date to take an award back to "earned, not announced". Slides show what is earned and in no night here and not held. |
| `held` | Optional: `[id] = { award: 1 }` for awards **held off the slides** (the Hold box on the Awards tab and the Progress record, one flag). A held award is skipped by *Mark all announced* and stays held until released; it is cleared by nothing else. Left out of the file while empty. An app older than 1.50.28 drops it when it saves, so every copy in use should be updated before holds are relied on. |
| `flags` | Optional: `[flagId] = { kid, level, book, block, key, note, at }`, a note pinned to a place for later review (`level` is `child`, `sheet`, `block` or `box`; `book` is the Progress book code, or `common` for the sections every Sparks sheet shares; `key` is the date box such as `GJ1.2`). Set with the flags on the Progress sheet, listed on the To do tab, deleted when cleared. Left out of the file while empty; an app older than 1.50.32 drops it when it saves. |
| `given` | `[id][award] = date`: the day the award was handed to the child, set on the Progress record only (room leaders). It does not wait for the award to be announced, and clearing an announcement never touches it. If it was handed over but nobody knows the day, the date is the day the box was ticked and the award is also listed in `givenNoDate`. |
| `givenNoDate` | Optional: `[id] = [award, ...]` for awards given with **no date** (the *no date* tick on the Awards chip and the Progress record). Left out of the file while empty, so most files do not change. `Season.givenShown` is empty for these, so no screen or report shows the ticked day as a given date; the Achievement Record prints "✓ (no date)". A real date typed later replaces the mark. An app older than 1.50.4 drops the list when it saves, and the ticked day would then show as a real date. (Uniforms keep their own equivalent: `x_Uni_GivenFlag`.) |
| `adults` | `[date] = [{ n: name, a: award }]` for the Adult Memorization slide only; adults are not in the roster. |
| `teamMoves` | `[id] = [{ q, from, team }]`: a mid-quarter color change. The roster's `team:Qn` is the quarter default. |
| `handbooks` | `[id] = "HG 260916 note"`: book code, date received (yymmdd) and an optional note, in one string (the old Sheet's format). The app edits the three parts in separate boxes. |
| `progress` | `[id][book][block.item] = date` for the Achievement Record sections. A Sparks jewel earns its award on items 1-4 (earned date = the latest of them); items 5-8 are its reviews and count only toward the book's Review Emblem (all eight jewels' sections and reviews; Rank is not part of it). T&T Silver and Gold units 1-4 earn their own patches; the Extra Credit emblems stay manual. |
| `config` | Award lists per group, slide exclusions (the app has no editor for these; they are fixed in the code's defaults and an older file's values are still read), book codes (2 or 3 letters that are the key itself: `HG`, `WR`, `SS`, `HC`, `AoG` = Agents of Grace, T&T; each has a `group`, and only Sparks books get a tab on the Progress screen; matching ignores case and an older two-letter spelling that starts like exactly one book still finds it; a file with `AO` plus `spell: AoG` is moved to `AoG` when opened), Blue Jewel weeks, place points, progress templates, club day, and optional `slideNames` (award wording for the slide pictures). |
| `config.teamPlan` | Optional, left out of the file while empty: `locked` = `{ Q3: 'yyyy-mm-dd' }` (quarters locked by hand, with the day), `proj` = `{ <id>: 'RB--' }` (the color the engine projected for each quarter, R B G Y or `-`), `prio` = `{ order, off }` (the three orderable balancing goals, only when they differ from the defaults). A color in an open quarter is a **pin** when it differs from its projected mark (or when the file has no marks at all, as in every older file), so nothing already entered is ever moved. A new year or *Start new year* clears it. Older apps keep it untouched (unknown `config` keys survive). Details: `COLOR-TEAMS.md`. |
| `history` | Every change as old/new at a path, so any version can be rebuilt, compared or restored (History tab). |

**Rules the app follows**
- A child's game points are never stored. They are worked out when needed: nights present × that night's team result (in the group stamped on that night's mark, else the child's group now) × the child's team on that night. Team on a night = the one-night team, else the latest move in that quarter on or before the date, else the quarter color. A move counts from its own night to the end of the quarter.
- Planning Center is never edited here. A change to one of its fields becomes a pending change (`ov:`) that shows in reports until a later export matches it.
- People who leave Planning Center are marked inactive, not deleted, so their history stays.
- **The complete JSON format is specified in `docs/DATA-FORMAT.md`** (every section, encoded value, marker and rule, with a worked example); `test/data-format-doc.test.js` keeps it in step with the code.
- Opening a file written by an older version upgrades it in memory (version 4 replaces the old one-box-per-jewel Sparks template and renames `SS Review Emblem - Yellow` to Red); the next download writes the current format. A file from a newer version is refused. **Version 6** (R17) adds `roster.pcExport` and keeps keys the app does not know: an older copy would drop them without a trace, so it refuses a version 6 file, and **every leader's copy must be updated before opening a file saved by the new one** (an emergency downgrade is described in `docs/DATA-FORMAT.md` 4.2). **Version 5** keeps the file small: it is written without indentation, and each person's Planning Center record is a list of values in the order of `roster.pcCols` (the export column order the file already keeps) or, when that does not cover every field, `roster.pcKeys` (the field names once, not per person); in memory the record is still the usual `{ field: value }` object (`packRoster` / `unpackRoster` in `season.js`, applied only in `toJson` / `fromJson`). Version 4 and older files, with objects per person, open unchanged. An app older than 1.46.0 refuses a version 5 file with its "newer version" message. Nothing derived (totals, pace, standings) is ever stored.

**Nothing is kept in the browser.** The report title is in the data file (`config.clubTitle`); a quarter picked by hand on Reports is kept in memory for this page and lapses after 7 days, then the quarter follows the calendar (the latest club night on or before today). Older copies kept some settings in the browser; `app.js` removes those keys on load.

## Using it

The in-app **How it works** tab is the user manual (every tab, one by one, plus the weekly routine and troubleshooting). Short version: open the newest data file and, when you want updates, this week's Planning Center export together (Import…); enter the night on the Attendance, Games and Awards tabs; Person (with its Progress sheet) for one child; print from Reports (on the Awards tab's Hand out page, *Printable list by class…* is the room leaders' list of awards earned and not given; *Slide images…* on the Announce page makes the TV slides from what is earned and not yet announced, and *Mark all announced* clears them once they have been shown); Download data file when you are done.

Tabs, in four groups (the same order on the desktop strip; on a phone each group is a heading in the tab menu): **Tonight** (To do, Attendance, Color team games, Awards), **People** (Roster, Person, Uniforms), **Season** (Calendar, Statistics, Awana store points, Reports), **Admin** (History, Options, How it works, Validate, Debug); a child's Progress sheet is a sub-tab of Person, and Validate and Debug show only when needed.

**Undo / Redo** step back through the session's edits (a tick, a note, a team move, a whole import) and are themselves logged in History. They keep the last 100 edits for this session only, and Ctrl+Z / Ctrl+Y work outside text boxes.

**After an import** the **To do** tab opens by itself. It shows the file check for the export (errors and warnings about the file: missing birthdates, grades that do not fit the age, unknown rooms, invalid emails, odd names, duplicates, cancelled registrations), what the import did, and what still needs doing (classes to assign, color teams, handbooks, uniforms, balances, missing details, medical notes of new people, changes to make in Planning Center). In *Group by task*, the handbook group has **Set book for all**: pick a book and press *Set* to give it to everyone listed who has no book yet (their date and note are kept; anyone who already has a book is skipped), for example every T&T child without a book set to AoG. Awards are not on this page: the Awards tab's own number counts the awards still to announce or hand out. The rules behind the checks live in `intake.js`; the list is computed by `todo.js` from the roster as it is now, so it shrinks as you fix things. Each item can be **ignored** (accepted as it is) for the session: it is hidden and not counted until the page is reloaded, and nothing is written to the data file.

**Test files:** if any file you open has TEST as a word in its name (`… TEST.csv`, `_test_`, any capitals; not "latest"), a red banner appears, every download is named with `TEST` before the date tag (`awana-2026-27-TEST-20261104-190000.json`) and the download buttons need two presses. Reload the page to clear it. This keeps the generated import test file from ever being saved over real data by accident.

**Slide images** (Awards tab) draw the Cubbies, Sparks, T&T and Adult Memorization slides as 1920×1080 PNGs from the awards earned and not yet announced (and not held), singly or as a ZIP; the night picked only titles the Adult Memorization slide. The Poppins font is embedded in `fonts.css` so the pictures look the same on any machine; there are no image assets.

## Tests

Running the suite: `sh dev/tools/run-tests.sh` runs everything, 4 tests at a time, and prints a line as each test starts and finishes, with a heartbeat every 30 seconds (what is still running, and any test over 120 seconds is marked slow). The same lines go to a progress file whose path is printed first, so `tail -f` on it from another window shows the run. Options: `--node-only` (no browser tests), `--changed` (the node tests, plus the browser tests that name a file changed since the last commit), a name filter, and `JOBS=6` to run more at once.

**Run everything:** `NODE_PATH=<dir with playwright> sh dev/tools/run-tests.sh [--node-only] [name-filter]` runs every `dev/app/test/*.test.js` four at a time and prints `ok`, `FAIL` or `SKIP` per file, then a summary; it exits non-zero only if a file failed. `--node-only` skips the browser tests (they are also skipped when `playwright` does not resolve). `roster.test.js` and `import-test-file.test.js` use the invented files in `dev/test-data/` when given no arguments; `browser.test.js`, `anonymized-data.test.js` and `reports-season.test.js` need real files and print `SKIP: needs real files` without them (run those by hand, below). `test/no-args.test.js` and `test/gitignore.test.js` pin both rules.

## Changing and deploying

1. Edit in `dev/app/`. Bump the version line of every `.js` file and the `app-version` / `app-build` meta tags in `index.html` that you changed (Mike's rule for now: stay in the 1.51.x series (since 1.51.00, Nov 12) and bump only the third number for every deployable change, features included; the minor number waits until leaders are told about releases. Never change the data-file format version for this). `make-deploy.sh` refuses to refresh `deploy/` if a changed file kept its old version.
2. Run the tests. Add a test for anything new.
3. `./make-deploy.sh` (run `npm install` in this folder once first: it fetches terser, the only build tool; the app has no dependencies). It minifies every script into `deploy/app/` (line 1, the version registration, is kept as written, so the Debug tab and the version check still work); `style.css`, `fonts.css` and the page are copied. A comment-only edit does not change the minified file and so needs no version bump. Then commit `deploy/` and push it to `main`: the GitHub Pages workflow publishes it. The Nextcloud copy is no longer updated.
4. Commit the rebuilt `deploy/` with the code (it is tracked). Deploy only when asked.
5. Hard-refresh the page. The splash screen and the header show the version; the Debug tab shows every file's version and date.
6. **After a deploy, update the version history page.** Run `node dev/tools/changelog-html.js version-history.html` and commit the result with the release; it lives in the project root and is not deployed. Also publish the same file with the Artifact tool to the private link https://claude.ai/artifact/DSVoBfFjNvpxf1WcYdeyT5 (only the owner can open it until shared). It is built from CHANGELOG.md, so add the entry for the release first.

Script load order matters and is enforced by `versions.test.js`: `csv, info, model, calendar, rotation, teams, catalog, season, datamerge, flagtrail, teamplan, pace, intake, check, validate, todo, reports, reports-season, slides, stats, store, app, app-ask, app-season, app-person, app-todo, app-teamgrid, app-stats, app-store, app-options, app-update, app-sw, app-info, app-flagpop, app-help, app-trail, app-merge, app-flagmode, app-flagmarks, app-tools, app-search, app-topbar`, then the optional Drive files `drive-config, drive, app-drive`.
