## 1. Grace applied backwards in time (blocking)

**Problem:** `dev/app/season.js` `blueJewelRequirements` (about lines 735–739) removes every excused night from every threshold, including thresholds a child reached before the cancelled night. This moves earlier earned Blue Jewel dates, and a dropped jewel can reappear (`blueWingPlan` matches by `n|date`, about lines 781–782). Reports print the lowered count too (`reports-season.js` about line 128).

**Required:** for each threshold, the reduction applies only if the child reached that threshold **after** the cancelled date. A threshold reached on or before the cancelled date keeps its original requirement and its original earned date. Apply the same rule everywhere the grace count is used, including the printed report.

**Tests:** with weeks [2,4], five nights attended, and the last night cancelled with activity: jewel 1 keeps 2026-09-09, jewel 2 keeps 2026-09-23, and a drop on `1|2026-09-09` still applies. Add a case where a threshold is reached after the cancelled night and is lowered.

## 2. Grace marker not tied to its date (blocking)

**Problem:** `app.js` (about line 1629) copies the row on a Date edit, so the excused marker moves with the row. `markRecordedClosure` runs only on State/Type edits, and nothing clears the marker when the night's records are removed. Grace and the season-start anchor (`season.js` about line 1419) can then apply to a night with no activity.

**Required:**
- The marker applies only while the night has recorded activity **on its own date**. Compute this from the records on the date, not from the stored marker alone.
- When a Date edit moves an excused row, clear the marker on the new row unless the new date has recorded activity (in which case the note dialog applies again).
- When records on an excused night are removed, the grace and season-start anchor stop applying.
- Keep the marker in the calendar row so it survives reload and CSV.

**Tests:** move an excused row to an empty date: requirements and season start unchanged from the no-marker case. Remove the last record on an excused night: grace stops. The marker survives reload.

## 3. State and Type edits skip checks (blocking)

**Problem:** `app.js` (about lines 1556–1558): when `!isExcused(row) || !n.recorded`, the State/Type edit goes straight to `finish()`. Examples: No club → Meets in a locked quarter; Event → Club night on a past date with attendance (the night silently starts counting); re-opening a past planned night. These were blocked or confirmed at HEAD.

**Required:** restore the confirmations and blocks that applied before round 4 for every State/Type edit that is **not** the excusing case. The excusing case (cancelling a night with recorded activity) keeps the note dialog from round 4. Everything else goes through the existing comparison and blocks as before.

**Tests:** No club → Meets in a locked quarter: blocked or confirmed as at HEAD. Event → Club night on a past date with attendance: confirmed or blocked as at HEAD. Cancelling a night with activity: note dialog, no block.

## 4. Quarter lock recalculates from the first counted night (owner decision C)

**Problem:** `dev/app/teamplan.js` `firstNight` (about line 51) and `reports.js` (about lines 415, 418) use `Calendar.nights` / `isNight`, which ignore the excused rule. A quarter whose only past night is cancelled with activity can look as if its first night is in the future. Its lock can flip and its colours recalculate.

**Required:** the quarter's first night for lock purposes is the first night that is counted or excused-with-activity. Recalculation follows the calendar as it changes, so a cancelled first night does not lock the quarter in its old state. Do not change stored hand locks; they stay as they are.

**Tests:** a quarter whose only past night is cancelled with activity: lock status recalculates as at owner decision C. A hand lock is unchanged.

## 5. Blocked browser storage breaks every in-place save (blocking)

**Required:** if browser storage is unavailable, keep the pending entry in memory for the session and show one clear message: "This browser will not keep save checks between reloads. Save a local copy before closing." Saves still work. Do not fail every save.

**Tests:** storage throws: a save succeeds, one message is shown, and `verifyReopened` does not alert on every open.
