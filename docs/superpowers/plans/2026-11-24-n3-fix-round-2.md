# N3 fix round 2 (brief for Codex)

**Source:** the Opus review of the round-1 changes (uncommitted, worktree `n-backlog-integration`, HEAD 13c1cfb). Round 1 is not ready for 1.51.22 as it stands. This brief fixes the blocking findings and records the owner's decisions.

**Owner decisions (2026-11-24):**
1. Deletes and date moves on nights with recorded activity are **allowed**, never refused outright. Require a strong warning: three separate confirmations, and the leader types a set phrase (`DELETE NIGHT` or `MOVE NIGHT`) to proceed. Show the records, quarters and reports that will change. One History entry and one Undo step.
2. **Deleting a future-planned night after the season has started is allowed but atypical.** Treat it as its own case: the leader may reconfigure the calendar as needed, but the warning says this is unusual and names the planned night. A "future-planned" night is a row dated after the season's first club night and after today. It uses the same three-step confirmation and typed phrase as decision 1, with the phrase `DELETE PLANNED NIGHT`.
3. **Any date can be entered.** Do not block a calendar entry because it is not a club night, and do not block a first calendar. Show a temporary, non-blocking notice when a date is not a club night: say a special event or a different type of meeting might be on that date. Let the leader continue with one click.

**Rules (AGENTS.md):** no commit, no push. Run only the closest test files or `--node-only`; do not run the full suite. No real names or personal data in code, fixtures or docs. Keep `dev/app/drive-config.js` empty. Do not hand-edit `deploy/`. Model: GPT Astra, Medium.

## A. Drive save: restore the post-write check (blocking)

**Problem:** the save relies on an If-Match check that the Drive v2 docs do not confirm is enforced. Round 1 removed the check that ran after each write, so if the check is not enforced, a save can overwrite a newer edit silently.

**Required:**
- After every write, list the file's revisions. Confirm that the revision immediately before ours is the one the save was built on. If not, do not treat the save as successful: read the newer revision, merge it, and write again within the existing retry limit. Restore the removed behaviour from the pre-round-1 version of `app-drive.js` rather than inventing a new one.
- Revision IDs from the v2 and v3 APIs must be compared only after normalising, or you must use one API consistently for the comparison. Check the docs for the exact format. If they differ in format, fail closed with a clear message and do not loop.
- Keep the conditional write, and keep refusing a missing, weak or `*` ETag.

**Tests:**
- A fake server that **ignores** If-Match. Assert that the post-write revision check still detects the overwritten newer edit and that the save merges and retries rather than reporting success.
- A test where the v2 and v3 revision strings differ in format. Assert the save fails closed with a message, with no loop.

## B. Paused calendar review lets a manual save skip the merge screen (blocking)

**Problem:** `dev/app/app-drive.js` around line 135: `let approved = !!c.review`. After autosave pauses on a calendar conflict, a later manual save can skip the merge summary, so changes (including removals) reach Drive unseen.

**Required:** a manual save must show the merge summary whenever the remote revision or the merge plan differs from the one the leader last approved. Tie approval to the specific remote revision and plan fingerprint. Reuse an earlier approval only when both still match.

**Tests:** a paused review followed by a manual save with no new conflicts must still open the summary. Add a test where the remote head moves between the pause and the manual save: the summary must reappear.

## C. Protected edits: warnings, not refusals (non-blocking for Fix C)

**Tests:** a three-step confirm that requires the typed phrase (wrong phrase blocks); a delete of a future-planned night after season start requires the `DELETE PLANNED NIGHT` phrase and shows the atypical warning; one Undo restores the night and its records.

## D. Date entry: any date allowed, notice only

**Required, in `calendar-safety.js` (the `compare` rule that blocks sign-offs before the first night) and `app-calendar-maker.js`:**
- Remove the rule that blocks a first calendar, or any calendar, because sign-offs fall before its first night. Replace it with a non-blocking notice listing the affected sign-offs and the new first night, so the leader can see what is outside the calendar.
- The per-date notice: when a date is not a club night, show a temporary notice saying a special event or a different meeting may be on that date. It disappears on its own or on the next action.
- Keep the cutoff choice from round 1 only as an optional helper; do not require it.
- Keep Apply enabled when the only issue is a notice. Keep it disabled for genuine data problems (invalid dates, duplicate nights, quarter order, or a change that would move recorded activity without the typed confirm).

**Tests:** a first calendar with earlier sign-offs applies with a notice; a non-club date shows the notice and can still be saved; a genuine data problem still blocks Apply.
