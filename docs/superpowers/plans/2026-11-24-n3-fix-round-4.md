## 1. Cancelled night drops out of totals and season start (blocking)

**Problem:** `dev/app/app.js` State/Type branch (about lines 1554–1580) shows the child-count dialog but does not exclude the night. `Season.counted` (`season.js` about line 699) and `nightList` read a `Recorded Night` column that nothing writes, so a cancelled night with activity still changes totals, and if it is the first night, the season start moves.

**Required:**
- When a night with recorded activity is set to Cancelled or No club, or its Type changes so that it no longer counts, mark it so totals and season start skip it. Write the marker through the calendar row (`Recorded Night` or the existing field), so the rule works on reload and in reports.
- Apply the attendance award grace: for any award that needs a number of attendance nights, the requirement drops by one per cancelled night with activity, for every child. Record no credit.
- Season start is computed from counted nights only, so a cancelled first night does not move it.
- Keep the records in place. Do not remove or move anything.
- Update the dialog text so it says what happens: the night stops counting toward totals and awards requirements, and the records stay.

**Tests:**
- Cancel the first night with attendance and one sign-off: season start unchanged; totals drop by the night; sign-off still listed as recorded.
- A cancelled night with attendance lowers the attendance requirement by one for a child with the same attendance count; no credit appears on that night.
- A night without activity cancelled: no dialog, no grace.
- Undo restores the marker and totals in one step.

## 2. Reopen clears a pending save without checking it (blocking)

**Problem:** `dev/app/app-drive.js` `openPicksRun` (about lines 101–106) calls `D.clearPending` after opening and does nothing else. A lost reply followed by a reload is never verified, and a displaced revision is never pinned or named.

**Required:** before clearing a pending entry on reopen, run the same previous-revision check used in recovery. Pin and name any displaced revision. Clear the entry only after that check succeeds or after the displaced revision is pinned. If the open did not complete, do not clear. Message the leader plainly with the file name.

**Tests:** a pending entry with a displaced revision: reopen pins the displaced revision and clears the entry; a failed open keeps the entry; a reopen with no pending entry is unchanged.

## 3. Moving an existing season's first night later is a notice, not a block

**Problem:** `dev/app/calendar-safety.js` `compare` (about lines 137–146) blocks when `date < afterStart && date >= beforeStart`. The round-3 change made this a notice whenever `beforeStart` exists, but the State path shows no dialog for it.

**Required:** restore the block only for the case the owner decided against: none. Make it a notice for all cases where a first night moves later. Show the affected records in a notice; Apply stays enabled.

**Tests:** deleting the first night of an existing season: notice, Apply enabled, records unchanged. A first calendar with earlier awards: notice (from round 3).

## 4. Two tabs overwrite each other's pending entries (minor)

**Problem:** `setPending` writes `new Map(pendingWrites)` from one tab's memory to one shared key, `awana-drive-pending`, which can drop another tab's entry.

**Required:** read the stored entries, merge in this tab's change for its own file id only, then write. Do not drop other files' entries.

**Tests:** two maps for two files written in turn: both entries survive.
